EasyViewer(Pagelight) 저장소의 README.md·README.en.md 헤더(제목, 배지, 언어 전환, 포크 안내, 라이선스 안내의 순서와 흐름)를 형제 프로젝트 Ezenitac-AiService/ImageViewer의 README 헤더 구성을 참고해 정리하고, 두 저장소 README를 비교해 서로 빠진 내용(절 구성)을 점검해 EasyViewer 쪽 공개 문서(README, CONTRIBUTING, SECURITY, CHANGELOG, NOTICE, THIRD_PARTY_LICENSES의 국문·영문 쌍)의 구조·흐름·용어를 일관되게 정리한다. 헌법 v6.1.0(제1원칙 국문·영문 병행, 지원 범위 단일 원문, 제8원칙 표현 원칙)을 준수한다."

## 배경

저장소 첫 화면(README)은 처음 온 사용자가 "무슨 앱인지, 어디서 받는지, 원저작자 앱과 무엇이 다른지"를 판단하는 곳이다. 2026-11-24 기준으로 두 형제 저장소의 README를 비교한 결과는 다음과 같다.

| 항목 | Pagelight(이 저장소) | ImageViewer(형제 프로젝트) |
|---|---|---|
| 헤더 순서 | 제목 → 언어 전환 → 영문 배너와 지원 범위 원문 6줄(인용) → 한 줄 소개 → 배지 → 포크 안내 → 라이선스 안내 | 제목 → 언어 전환 → 배지 → 한 문단 소개 → 처음 실행 경고 → 포크 안내 |
| 플랫폼 배지 | 4개 플랫폼을 같은 무게로 나열, 링크가 "지원 기능" 절로 감 | 우선순위 등급을 배지 글자에 표시, 링크가 "지원 플랫폼" 절로 감 |
| 처음 실행 안내(공증 전 macOS 확인) | 문서 중간 "macOS 설치" 절에만 있음 | 헤더 바로 아래 강조 안내 |
| 원저작자 앱과의 차이 | 문서 끝 | 헤더 바로 다음 |
| 지원 플랫폼과 릴리스 파일 | 국문은 헤더 인용 안에만, 영문은 별도 절 | 등급·파일·상태를 한 표로 |
| 조작 방법(단축키) | 없음 | 있음 |
| 기여·보안 안내 절 | 없음(헤더 문장 하나) | 있음 |
| 개발자용 상세(디렉터리 구조, 검증 스크립트, 버전 동기화, 릴리스 절차) | README 안에 길게 있음(약 300줄의 절반 이상) | 기여 가이드로 넘김(README 약 125줄) |

같은 저장소 안에서도 국문 README와 영문 README의 절 구성이 다르다(국문은 지원 범위를 헤더 인용에 넣고, 영문은 "Supported platforms" 절을 따로 둔다). 나머지 공개 문서는 언어 전환 줄 위치는 맞지만 제목 형식(예: "변경 이력 (CHANGELOG)", "서드파티 오픈소스 라이선스 고지 (Third-Party Licenses)", "기여 가이드")과 원저작자를 부르는 말("원저작자", "원작", "업스트림")이 문서마다 다르다.

형제 프로젝트의 README는 절대 기준이 아니라 참고 자료다. 정리의 기준은 이 저장소 독자가 첫 화면에서 판단해야 할 것(US1의 다섯 질문)과 헌법 v6.1.0이다. 형제 프로젝트에서 빌려 온 구성이라도 이 기준에 맞지 않으면 따르지 않고, 형제 프로젝트에 없는 이 저장소의 장점(검증 가능한 차이 표, 최소 요구 사양, 지원 범위 단일 원문)은 유지하며, 형제 프로젝트의 표현 가운데 이 저장소의 표현 원칙에 맞지 않는 말은 들여오지 않는다.

## Clarifications

### Session 2026-11-24

- Q: 형제 프로젝트(ImageViewer) README는 이 정리에서 어떤 지위인가? → A: 절대 기준이 아니라 참고 자료다. 헤더 순서·배지·절 구성은 이 저장소 독자의 필요(US1 다섯 질문)와 헌법을 기준으로 정하고, 형제 프로젝트와 같거나 달라도 된다. 두 저장소를 똑같이 맞추는 것은 목표가 아니다.
- Q: README 안의 개발자용 상세(디렉터리 구조, 검증 스크립트, 버전 동기화, 릴리스 절차)를 어디에 두는가? → A: 기여 가이드(필요하면 운영 문서)로 옮기고, README에는 "개발·기여" 절에 요약 몇 줄과 링크만 둔다.
- Q: 지원 범위 원문 블록(6줄)을 README 헤더에 두는가, "지원 플랫폼과 릴리스" 절로 옮기는가? → A: 헤더에는 영문 한 줄 배너만 두고, 원문 블록은 국문·영문 모두 "지원 플랫폼과 릴리스" 절 맨 위에 둔다.
- Q: 원저작자 쪽을 가리키는 표준 용어는 무엇인가? → A: 사람·저장소·앱은 "원저작자"·"원저작자 저장소"·"원저작자 앱"(영문 original author, original repository, original app)으로 쓰고, "업스트림"(upstream)은 병합·동기화 금지 같은 Git 작업 맥락에서만 허용한다. "원작"·"원본"은 쓰지 않는다(과거 이력 기록과 인용은 예외).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 처음 온 사용자가 첫 화면에서 앱과 받는 곳을 이해한다 (Priority: P1)

저장소를 처음 연 사용자는 스크롤을 거의 하지 않고도 이 앱이 무엇이고(TXT·EPUB 뷰어), 원저작자 앱에서 갈라진 독립 포크이며, 어느 플랫폼을 어떤 수준으로 지원하는지, 어디서 받고 macOS에서 처음 실행할 때 무엇을 해야 하는지를 안다. 국문 첫 화면과 영문 첫 화면은 같은 순서로 같은 정보를 준다.

**Why this priority**: 첫 화면에서 판단하지 못하면 사용자는 잘못된 앱을 받거나(원저작자 앱과 혼동), 처음 실행에서 막히거나, 원저작자 저장소에 이슈를 올린다. 이 셋은 헌법 제8원칙이 막으려는 문제다.

**Independent Test**: 국문·영문 README의 헤더 영역만 보고 다음 다섯 질문에 답할 수 있는지 확인한다: 무슨 앱인가, 원저작자 앱과의 관계는, 지원 등급은, 어디서 받는가, macOS 처음 실행 시 무엇을 하는가. 두 언어의 헤더 요소 순서가 같은지 대조한다. 형제 프로젝트와 순서가 같은지는 판정 기준이 아니다.

**Acceptance Scenarios**:

1. **Given** 국문 README, **When** 헤더 영역을 읽으면, **Then** 제목 → 언어 전환 → 배지 → 영문 한 줄 배너 → 한 문단 소개 → 처음 실행 안내 → 독립 포크·이슈 등록 안내 순서로 나오고, 지원 범위 원문 블록은 헤더에 없다.
2. **Given** 영문 README, **When** 헤더 영역을 읽으면, **Then** 국문과 같은 순서로 같은 요소가 나온다.
3. **Given** 플랫폼 배지, **When** 읽으면, **Then** 중점·유지·테스트 빌드 등급이 드러나고 Windows는 없으며, 누르면 같은 언어 문서의 지원 플랫폼 절로 간다.
4. **Given** 헤더의 모든 배지와 링크, **When** 누르면, **Then** 깨진 링크가 하나도 없다.

### User Story 2 - 사용자 정보가 앞에, 개발자 정보가 뒤나 기여 문서에 있다 (Priority: P2)

README 본문은 사용자가 필요한 순서(원저작자 앱과의 차이 → 지원 플랫폼과 릴리스 파일 → 기능 → 조작 방법 → 설치 → 소스 빌드 → 개발·기여와 보안 → 라이선스)로 읽히고, 개발자용 상세는 기여 가이드(필요하면 운영 문서)로 옮겨 README에는 요약과 링크만 남는다. 형제 프로젝트에 있고 이 저장소에 없던 절(지원 플랫폼·릴리스 표, 조작 방법, 기여·보안 안내)이 생기고, 이 저장소에만 있던 유용한 절(최소 요구 사양, 검증 가능한 차이 표)은 남는다.

**Why this priority**: 지금 README의 절반 이상이 개발자용이라 사용자 정보가 묻힌다. 하지만 헤더(P1)보다 영향 범위가 크고 내용 이동이 많아 뒤에 둔다.

**Independent Test**: README의 절 순서를 목록으로 뽑아 위 순서와 대조하고, 옮긴 개발자용 내용이 모두 새 위치에 있는지(빠진 내용 없음) 확인한다.

**Acceptance Scenarios**:

1. **Given** 국문·영문 README, **When** 절 제목을 순서대로 뽑으면, **Then** 두 언어의 절 수와 순서가 같다.
2. **Given** 지원 플랫폼과 릴리스 절, **When** 읽으면, **Then** 플랫폼마다 등급·최소 버전·릴리스 파일·상태가 한 표에 있고, Linux·Android 파일이 테스트용 빌드임이 드러난다.
3. **Given** 조작 방법 절, **When** 읽으면, **Then** 앱이 실제로 지원하는 키보드·마우스·터치 조작만 있다.
4. **Given** 개발자용 상세 내용, **When** 정리 전후를 비교하면, **Then** 정리 전 README에 있던 개발자용 정보가 하나도 사라지지 않고 기여 가이드(필요하면 운영 문서)에 있으며, README의 "개발·기여" 절에는 요약 몇 줄과 그 위치 링크가 있다.

### User Story 3 - 모든 공개 문서가 같은 형식과 용어를 쓴다 (Priority: P3)

README, CONTRIBUTING, SECURITY, CHANGELOG, NOTICE, THIRD_PARTY_LICENSES의 국문·영문 쌍이 같은 제목 형식, 같은 맨 위 구성(제목 → 언어 전환 → 한 줄 목적), 같은 용어를 쓰고, 쌍끼리 절 구성이 같다.

**Why this priority**: 형식과 용어가 문서마다 다르면 읽는 사람이 같은 대상을 다른 것으로 오해한다(예: "원작"과 "원저작자 앱"). 사용자 영향은 P1·P2보다 작다.

**Independent Test**: 여섯 쌍의 맨 위 세 요소와 절 제목 목록을 뽑아 비교하고, 용어표에 없는 동의어가 남아 있는지 찾는다.

**Acceptance Scenarios**:

1. **Given** 여섯 쌍, **When** 각 문서의 맨 위를 보면, **Then** 제목 → 언어 전환 → 한 줄 목적 순서가 같다(NOTICE는 법적 고지 문서 형식을 유지하되 같은 순서).
2. **Given** 각 쌍, **When** 절 제목을 비교하면, **Then** 국문과 영문의 절 수와 순서가 같다.
3. **Given** 용어표, **When** 공개 문서 전체를 찾으면, **Then** 용어표에서 쓰지 않기로 한 동의어가 남아 있지 않다(인용·과거 이력 기록은 예외).

### Edge Cases

- 지원 범위 원문 블록(국문·영문)은 단일 원문에서 만든 그대로여야 한다. 헤더를 옮기면서 블록 문장을 손으로 고치면 안 된다.
- 영문 한 줄 포크 안내(배너)는 국문 README 첫 화면 안에 있어야 한다. 이 기능에서 "첫 화면"은 처음 15줄 안이면서 첫 `##` 절 제목보다 앞인 영역으로 정한다(언어 전환 검사와 같은 기준). 기존 기준(처음 12줄)은 새 헤더 순서에서 배지 하나만 늘어도 깨지므로 이 기준으로 바꾼다. 지원 범위 원문 블록을 헤더에서 "지원 플랫폼과 릴리스" 절로 옮겨도 블록 검사는 문서 안 위치와 관계없이 통과해야 한다.
- 형제 프로젝트 README의 표현 가운데 이 저장소의 금지 표현(예: 과거 버전을 낮추어 부르는 말)이나 원저작자를 대신 규정하는 문장은 들여오지 않는다.
- CHANGELOG의 과거 항목은 사실 기록이므로 형식(제목 단계, 용어)만 맞추고 내용은 바꾸지 않는다. 과거 항목 안의 옛 용어는 예외로 둘 수 있다.
- NOTICE는 법적 고지 문서다. 저작권·변경 고지 내용은 바꾸지 않고 맨 위 형식과 용어만 맞춘다. 영문판이 참고 번역이라는 표시는 유지한다.
- THIRD_PARTY_LICENSES는 자동 생성 내용이 있다. 생성 부분은 손으로 고치지 않고, 머리말만 정리한다.
- 보존 기록(`docs/windows-*.md`)과 `specs/` 아래 문서는 대상이 아니다.
- 배지가 가리키는 외부 서비스(배지 이미지 서버)가 일시적으로 응답하지 않을 수 있다. 링크 검사는 저장소 안 링크와 배지 링크 대상(이 저장소의 워크플로·릴리스·라이선스·원저작자 저장소)을 구분해 보고한다.
- 조작 방법 절에 앱이 지원하지 않는 단축키를 적으면 안 된다. 확인하지 못한 조작은 적지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (README 헤더 순서)**: 국문·영문 README의 헤더는 같은 순서여야 한다: 제목 → 언어 전환 → 배지 → 한 문단 소개(앱 종류, 현재 버전, 원저작자 앱에서 갈라진 독립 포크) → 처음 실행 안내(공증 전 macOS 확인, 상세 위치 링크) → 독립 포크·이슈 등록 안내(이 저장소에 신고, 원저작자 저장소에 올리지 않기, 보안 신고 경로). 영문 한 줄 배너는 배지 다음, 소개 문단 앞에 두어 국문 README 첫 화면 규칙을 지킨다. 지원 범위 원문 블록은 헤더에 두지 않는다. 라이선스 한 줄 안내는 헤더에서 빼고 라이선스 절로 옮긴다.
- **FR-002 (배지)**: 배지는 두 언어에서 같은 종류·같은 순서여야 하며, 각 배지는 독자가 판단에 쓰는 정보(빌드 상태, 최신 릴리스, 라이선스, 지원 플랫폼, 원저작자 출처 등)를 하나씩 담아야 한다. 정보가 겹치거나 독자 판단에 쓰이지 않는 배지는 두지 않는다. 배지 종류는 형제 프로젝트와 같을 필요가 없다. 플랫폼 배지는 지원 등급(중점 macOS, 유지 iOS, 테스트 빌드 Linux·Android)을 글자로 드러내고 Windows를 넣지 않으며, 같은 언어 문서의 지원 플랫폼 절로 연결해야 한다.
- **FR-003 (README 절 구성)**: README 본문 절은 두 언어에서 같은 수·같은 순서여야 하며, 사용자용 절(원저작자 앱과의 차이, 지원 플랫폼과 릴리스, 기능, 조작 방법, 설치와 처음 실행, 소스 빌드)이 개발자용 절보다 앞에 와야 한다. 마지막은 개발·기여와 보안 안내(개발자용 상세는 요약 몇 줄과 기여 가이드 링크), 라이선스와 저작권 고지 순서다.
- **FR-004 (지원 플랫폼과 릴리스 표)**: 지원 플랫폼 절은 맨 위에 지원 범위 원문 블록(국문 README는 국문 블록, 영문 README는 영문 블록)을 두고, 그 아래에 플랫폼마다 등급, 최소 버전, 릴리스 파일 형태, 상태를 한 표로 보여 주고, Linux·Android 파일 이름의 테스트용 빌드 표식과 체크섬 확인 방법을 안내해야 한다. 표의 등급·최소 버전은 지원 범위 단일 원문과 최소 요구 사양과 어긋나면 안 된다.
- **FR-005 (조작 방법 절)**: 앱이 실제로 지원하는 키보드·마우스·터치 조작을 표로 적어야 한다. 표에는 자동 테스트가 그 동작을 확인하는 조작만 적는다. 테스트가 없는 조작은 테스트를 추가하거나 표에서 뺀다.
- **FR-006 (내용 보존과 이동)**: 정리 전 README에 있던 정보는 모두 정리 후 어딘가에 남아야 한다. 개발자용 상세(디렉터리 구조, 검증 스크립트, 버전 동기화, 릴리스 절차)는 기여 가이드(국문·영문)로 옮기고, 운영자만 쓰는 절차는 운영 문서로 옮길 수 있다. README에는 "개발·기여" 절에 요약과 새 위치 링크를 둔다. 기여 가이드로 옮긴 내용은 국문·영문을 같은 변경에서 함께 옮긴다.
- **FR-007 (공개 문서 맨 위 형식)**: 여섯 쌍의 공개 문서는 제목 → 언어 전환 → 한 줄 목적 순서를 따라야 한다. README는 예외로, 언어 전환 다음에 FR-001의 헤더(배지, 배너)가 오고 헤더의 소개 문단을 목적 문장으로 본다. 영문판이 참고 번역인 문서(NOTICE, THIRD_PARTY_LICENSES)는 목적 문장 바로 다음에 참고 번역 표시를 두며, 이 표시는 반드시 남아 있어야 한다. 국문 제목은 한국어로, 영문 제목은 영어로 쓰고, 괄호 병기 형식을 문서마다 다르게 쓰지 않는다.
- **FR-008 (쌍 구조 일치)**: 각 국문·영문 쌍은 절 제목 수와 순서가 같아야 하며, 이를 자동 검사로 확인해야 한다.
- **FR-009 (용어 통일)**: 공개 문서가 쓰는 핵심 용어(원저작자·원저작자 저장소·원저작자 앱, 독립 포크, 지원 등급 이름, 테스트용 빌드, 소스 빌드, 보존 기록 등)를 국문·영문 대응표로 정하고, 공개 문서는 표의 용어만 써야 한다. 원저작자 쪽은 "원저작자"·"원저작자 저장소"·"원저작자 앱"(original author, original repository, original app)으로 쓰고, "업스트림"(upstream)은 병합·동기화 금지 같은 Git 작업 맥락에서만 쓴다. "원작"·"원본"(original work, upstream app 등 같은 뜻의 다른 말)은 쓰지 않는다. 과거 이력 기록과 인용은 예외다.
- **FR-010 (링크 무결성)**: 공개 문서 안의 저장소 내부 링크와 문서 내 앵커는 깨진 것이 없어야 하며, 이를 자동 검사로 확인해야 한다.
- **FR-011 (기존 규칙 유지)**: 지원 범위 원문 블록, 첫 화면 배너 위치, 금지 표현, 국문·영문 쌍과 언어 전환 링크, 앱 정체성, Windows 재유입 검사 등 기존 공개 문구 검사는 정리 후에도 모두 통과해야 한다.
- **FR-012 (형제 프로젝트 참고 범위)**: 형제 프로젝트 README는 참고 자료일 뿐 판정 기준이 아니다. 헤더 순서, 배지 구성, 절 흐름을 비교 대상으로 삼되, 채택 여부는 이 저장소 독자의 필요와 헌법으로 판단한다. 형제 프로젝트의 문장을 그대로 옮기지 않으며, 이 저장소의 표현 원칙(포크 자신의 범위만 서술, 원저작자 앱을 낮추어 평가하지 않음, 금지 표현)에 맞지 않는 말은 쓰지 않는다. 형제 프로젝트 저장소는 고치지 않는다.

### Key Entities

- **공개 문서 쌍**: 국문 기본 문서와 영문판. 맨 위 형식, 절 구성, 용어가 같아야 한다.
- **README 헤더**: 제목, 언어 전환, 배지 묶음, 소개 문단, 처음 실행 안내, 독립 포크·이슈 안내, 지원 범위.
- **배지**: 종류, 표시 글자, 연결 대상. 두 언어에서 같은 순서.
- **용어 대응표**: 핵심 용어의 국문·영문 표기, 허용 맥락(예: "업스트림"은 Git 작업 맥락만), 쓰지 않을 동의어(예: "원작", "원본").

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 국문·영문 README 헤더가 FR-001 순서를 100% 따르고, 두 언어의 헤더 요소 순서가 같다.
- **SC-002**: 처음 온 사용자가 README 첫 화면(헤더 영역)만 읽고 "무슨 앱인가, 원저작자 앱과의 관계, 지원 등급, 받는 곳, macOS 처음 실행 방법" 5개 질문에 모두 답할 수 있다(검토자 점검표 5/5).
- **SC-003**: 여섯 쌍 모두 국문·영문 절 수와 순서가 일치한다(6/6), 자동 검사로 확인한다.
- **SC-004**: 공개 문서의 저장소 내부 링크·앵커 중 깨진 것이 0개다.
- **SC-005**: 플랫폼 배지가 지원 등급을 드러내고, Windows 표기가 0개이며, 같은 언어의 지원 플랫폼 절로 연결된다.
- **SC-006**: 정리 전 README의 정보 항목 중 사라진 것이 0개다(정리 전후 대조표).
- **SC-007**: 용어 대응표에서 쓰지 않기로 한 동의어가 공개 문서(과거 이력·인용 제외)에 0개 남는다.
- **SC-008**: 기존 공개 문구 검사(지원 범위, 배너 위치, 금지 표현, 문서 쌍, 정체성, Windows 재유입)가 모두 통과한다.
- **SC-009**: README에서 사용자용 절이 모두 개발·기여 절보다 앞에 있고, README에 디렉터리 구조·검증 스크립트 목록·버전 동기화 파일 목록·릴리스 절차 본문이 남아 있지 않다(요약과 링크만).

## Assumptions

- 대상은 이 저장소의 공개 문서 여섯 쌍이다. `docs/` 아래 운영·안내 문서, `specs/`, 보존 기록은 대상이 아니다. 단, README에서 옮긴 내용을 받는 문서와, README·기여 가이드의 옛 앵커를 가리키는 링크(보존 기록 제외)는 예외로 고칠 수 있다.
- 형제 프로젝트 README는 2026-11-24 시점 내용을 참고했다. 이후 바뀌어도 이 기능의 기준은 바뀌지 않는다.
- 지원 범위 문장 자체는 바꾸지 않는다(헌법 v6.1.0 등급 그대로). 위치와 주변 흐름만 정리한다.
- 처음 실행 안내는 현재 릴리스가 Apple 공증을 받지 않은 상태를 기준으로 한다. 공증을 받으면 별도 변경으로 안내를 고친다.
- 조작 방법 절은 현재 앱 기능 범위 안의 조작만 다룬다. 새 단축키를 만들지 않는다.
- 배지 이미지 서버(외부)의 표시 여부는 이 기능의 검사 범위 밖이다. 배지 연결 대상이 맞는지만 확인한다.
- 문서 정리이므로 앱 동작, 릴리스 워크플로, 지원 범위 원문은 바뀌지 않는다.
