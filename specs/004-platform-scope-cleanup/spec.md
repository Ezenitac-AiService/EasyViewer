# Feature Specification: 지원 범위 재정렬과 독립 포크 분리 마무리

**Feature Branch**: `004-platform-scope-cleanup`

**Created**: 2026-11-24

**Status**: Implemented (2026-11-24): 자동 검사·문서·워크플로 구현 완료. 라벨 생성(T002)·PR CI(T046)·리허설과 기존 릴리스 노트 편집(T047–T049)은 메인테이너 승인 대기, macOS 실기기 항목(T051)은 BLOCKED

**Input**: User description: "개정된 헌법 v6.0.0을 준수하면서 독립 포크 분리 작업을 계속 진행하기 위한 후속 기능. (1) 지원 범위 반영: 중점 macOS(유일한 핵심 빌드), 유지 iOS(소스 빌드만), 테스트 빌드 Linux·Android(테스트용 빌드로 배포만, 품질·검증·대응 보장 없음), 제외 Windows를 지원 범위 단일 원문·공개 문서(국문·영문)·이슈 양식·앱 정보 화면에 반영. (2) 릴리스에서 Linux·Android 산출물을 테스트용 빌드로 분명히 표시하고, 표시 누락을 게시 전에 막음. Android는 포크 서명 키로만 게시하는 규칙 유지. (3) Windows 완전 제외: 남은 Windows 전용 코드·설정·빌드 스크립트·의존성 감사 대상·사용 안내 문서를 제거하되, 원저작자 앱 안내 문장과 기존 Windows 프리릴리스의 지원 종료 이력은 보존. (4) 003 독립 포크 분리 작업의 남은 항목 정리: Windows 전환 검증(T048·T049) 범위 제외, Linux·Android 실기기 검증 항목을 테스트 빌드 기준으로 재조정, 003 스펙 상태를 실제 결과로 갱신."

## 배경

헌법 v6.0.0은 플랫폼 등급을 다시 정했다.

| 등급 | 플랫폼 | 약속 |
|---|---|---|
| 중점 | macOS | 유일한 핵심 빌드. 설계·검증·품질 투자의 기준 |
| 유지(후순위) | iOS | 소스 빌드로만 제공. 실패는 고친다 |
| 테스트 빌드(최하위) | Linux, Android | 테스트용 빌드로 배포만 한다. 품질·기능 동등성·실기기 검증·대응 일정을 보장하지 않는다 |
| 제외 | Windows | 배포·지원·CI·신규 코드·사용 안내 문서의 대상이 아니다. 남은 Windows 전용 요소는 제거한다 |

지금 저장소의 공개 문구·앱 정보 화면·릴리스 표기는 헌법 v5.0.0 기준(iOS·Linux·Android를 같은 "유지" 등급으로 묶음)에 머물러 있고, Windows 전용 코드와 설정이 남아 있다. 003 독립 포크 분리 작업에는 Windows 전환 검증처럼 더는 의미가 없는 항목과, 테스트 빌드 등급에 맞지 않는 실기기 검증 항목이 열려 있다. 이 기능은 이 차이를 없애고 003을 닫는다.

## Clarifications

### Session 2026-11-24

- Q: 릴리스할 때 Linux나 Android 테스트용 빌드가 실패하면 릴리스 전체를 어떻게 처리하는가? → A: 실패한 테스트용 빌드만 빼고 macOS(와 성공한 나머지)는 게시하며, 릴리스 노트에 해당 테스트용 빌드가 이번 릴리스에 없다는 문장을 자동으로 적는다.
- Q: Linux·Android 사용자의 버그 신고를 이슈로 받는가? → A: 받는다. 신고 전에 테스트용 빌드라 대응 일정을 보장하지 않는다는 안내를 보여 주고, 해당 신고에는 테스트 빌드 표시를 자동으로 붙인다.
- Q: Linux·Android 테스트용 빌드에서 보안 취약점이 발견되면 고칠 의무가 있는가? → A: 공통 코드의 취약점은 macOS와 함께 고친다. 테스트용 빌드에만 있는 취약점을 바로 고칠 수 없으면 고칠 때까지 그 플랫폼을 릴리스에서 빼고, 보안 정책과 릴리스 노트에 밝힌다.
- Q: Linux·Android 테스트용 빌드가 여러 릴리스에 걸쳐 계속 실패하면 어떻게 하는가? → A: 같은 플랫폼이 3회 연속 릴리스에서 빠지면 릴리스를 멈추고, 메인테이너가 고치거나 지원 범위에서 빼는 별도 변경을 결정하게 한다.
- Q: Linux 사용자 데이터 이전이 테스트용 빌드에서도 데이터를 잃지 않는다는 것을 무엇으로 확인하는가? → A: 자동 테스트로 확인한다. Linux 경로 규칙(원본 위치, 제외 폴더)을 포함한 이전 테스트가 모든 PR에서 통과해야 하며, 실기기 확인은 하지 않는다.
- Q: 영문 공개 문서의 지원 범위 설명이 한국어 원문과 같은 뜻인지 무엇으로 확인하는가? → A: 영문 지원 범위 문장도 단일 원문에서 생성해 영문 문서마다 블록으로 넣고, 한국어 블록과 같은 자동 검사로 비교한다.
- Q: 저장소에서 지울 "Windows 전용 요소"를 무엇을 기준으로 가려내는가? → A: 동작 기준. Windows용으로 빌드하거나 실행할 때만 효과가 있는 코드·설정·파일·스크립트·감사 대상만 지우고, 다른 플랫폼에도 효과가 있는 것(입력 검증, 대소문자 처리 등)은 남긴다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사용자가 플랫폼별 약속 수준을 정확히 안다 (Priority: P1)

새 사용자나 기존 사용자가 저장소 첫 화면, 릴리스 페이지, 앱 정보 화면 중 어디를 보더라도 macOS가 핵심이고 iOS는 소스 빌드만, Linux·Android는 테스트용 빌드이며 Windows는 범위 밖이라는 같은 내용을 읽는다.

**Why this priority**: 공개 문구가 실제 약속보다 크면 사용자가 지원받지 못할 플랫폼에 시간을 쓰고, 기대와 다른 품질에 실망한다. 헌법은 공개 문구가 지원 등급과 같은 의미일 것을 요구한다(MUST).

**Independent Test**: 공개 문서(국문·영문), 이슈 양식, 앱 정보 화면의 지원 범위 문구를 단일 원문과 대조해 의미가 어긋나는 곳이 0건인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장소 첫 화면을 연 사용자, **When** 맨 위 안내를 읽으면, **Then** macOS가 중점이고 iOS는 소스 빌드만, Linux·Android는 테스트용 빌드, Windows는 범위 밖이라는 내용을 국문과 영문 모두에서 확인할 수 있다.
2. **Given** 앱을 실행한 사용자, **When** 앱 정보 화면을 열면, **Then** 공개 문서와 같은 지원 범위 문구가 보인다.
3. **Given** Linux 또는 Android 사용자, **When** 버그를 신고하려고 이슈 양식을 열면, **Then** 이 플랫폼은 테스트용 빌드라서 대응 일정을 보장하지 않는다는 안내를 신고 전에 보고, 신고는 받아들여지며 테스트 빌드 표시가 자동으로 붙는다.
4. **Given** Windows 사용자, **When** 이슈 양식이나 문서에서 Windows를 찾으면, **Then** 이 포크는 Windows를 다루지 않고 원저작자 앱을 쓰라는 안내 한 가지만 본다.

### User Story 2 - 테스트용 빌드가 정식 빌드로 오해받지 않는다 (Priority: P1)

릴리스에서 Linux·Android 산출물을 내려받는 사람은 파일 이름과 릴리스 노트만 보고도 그것이 테스트용 빌드임을 알 수 있다. 메인테이너가 표시를 빠뜨리면 게시 전에 막힌다.

**Why this priority**: 헌법은 테스트 빌드 산출물에 테스트용임을 밝힐 것을 요구한다(MUST). 표시가 빠진 채 게시되면 공개 이후에는 되돌리기 어렵다.

**Independent Test**: 리허설 릴리스를 만들어 Linux·Android 산출물의 이름과 릴리스 노트에 테스트용 표시가 있는지 확인하고, 표시를 일부러 뺀 산출물로 게시 전 검사가 실패하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Linux 산출물이 포함된 릴리스, **When** 게시되면, **Then** Linux 파일 이름과 릴리스 노트가 모두 테스트용 빌드임을 밝힌다.
2. **Given** 포크 서명 키가 등록된 릴리스, **When** Android 산출물이 게시되면, **Then** APK 이름과 릴리스 노트가 테스트용 빌드임을 밝히고, APK는 포크 서명 키로 서명되어 있다.
3. **Given** 포크 서명 키가 없는 릴리스, **When** 게시되면, **Then** Android 산출물은 없고, debug 서명이나 임시 키로 서명한 APK도 없다.
4. **Given** 테스트용 표시가 빠진 Linux·Android 산출물, **When** 게시 전 검사를 실행하면, **Then** 검사가 실패하고 게시되지 않는다.
5. **Given** macOS 산출물, **When** 게시되면, **Then** 테스트용 표시가 붙지 않는다.
6. **Given** Linux 또는 Android 테스트용 빌드가 실패한 릴리스, **When** 게시가 진행되면, **Then** macOS와 성공한 나머지 산출물은 게시되고, 릴리스 노트에 실패한 테스트용 빌드가 이번 릴리스에 없다는 문장이 자동으로 들어간다.
7. **Given** macOS 빌드가 실패한 릴리스, **When** 게시가 진행되면, **Then** 릴리스 전체가 멈추고 아무것도 게시되지 않는다.

### User Story 3 - 저장소에 Windows를 위한 것이 남지 않는다 (Priority: P2)

메인테이너와 기여자는 저장소에서 Windows 전용 코드, 설정, 빌드 스크립트, 의존성 감사 대상, 사용 안내 문서를 더 이상 마주치지 않는다. 다만 원저작자 앱 안내 문장과 기존 Windows 프리릴리스의 지원 종료 이력은 남는다.

**Why this priority**: 헌법은 남은 Windows 전용 요소의 제거를 요구한다(MUST). 검증하지 않는 코드는 보안 결함을 숨긴다. 그러나 사용자 안내와 공개 이력보다 우선하지는 않는다.

**Independent Test**: 저장소 전체에서 Windows 전용 항목을 찾아, 허용 목록(원저작자 안내 문장, 지원 종료 이력, 과거 명세 기록, Windows 형식 경로를 거부하는 보안 검사) 밖에 남은 것이 0건인지 확인하고, 핵심 빌드와 모든 품질 검사가 그대로 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이 기능이 끝난 저장소, **When** Windows 전용 항목을 검사하면, **Then** 허용 목록 밖에서 0건이 나온다.
2. **Given** 이미 게시된 Windows 프리릴리스와 그 지원 종료 고지, **When** 이 기능이 끝난 뒤 확인하면, **Then** 릴리스, 산출물, 고지, 변경 이력의 지원 종료 기록이 그대로 남아 있다.
3. **Given** 지원 종료 고지에서 링크된 Windows 전환 안내, **When** 링크를 열면, **Then** 끊기지 않고 열리며, 그 문서는 더 이상 갱신하지 않는 보존 기록임이 표시되어 있다.
4. **Given** 이 기능이 끝난 저장소, **When** macOS 빌드와 전체 품질 검사를 실행하면, **Then** 모두 통과한다.
5. **Given** Windows 형식의 경로(드라이브 문자, 네트워크 공유 경로)가 담긴 입력, **When** 앱이 이를 받으면, **Then** 지금처럼 신뢰할 수 없는 입력으로 거부한다.

### User Story 4 - 003 독립 포크 분리가 닫힌다 (Priority: P2)

메인테이너는 003 작업 목록에서 무엇이 끝났고 무엇이 왜 범위 밖이 되었는지 한눈에 볼 수 있고, 003 스펙 상태가 실제 결과를 반영한다.

**Why this priority**: 분리는 이미 끝났고 첫 독립 릴리스도 나갔다. 열린 항목이 의미를 잃은 채 남아 있으면 진행 상황을 잘못 판단하게 된다.

**Independent Test**: 003 작업 목록의 열린 항목이 모두 완료, 범위 제외(사유와 근거 헌법 조항 포함), 또는 다음 기능으로 이관(이관처 명시) 중 하나로 분류되어 있는지, 003 스펙 상태가 실제 결과와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** Windows 전환 검증 항목(T048·T049), **When** 003을 정리하면, **Then** 헌법 v6.0.0의 Windows 제외를 근거로 범위 제외로 표시된다.
2. **Given** Linux·Android 실기기 검증 항목(Linux 이전 시나리오, Linux·Android 공존 설치, Android release 서명 강제의 로컬 확인), **When** 003을 정리하면, **Then** 테스트 빌드 기준에 맞게 "빌드·설치 가능 여부만 확인" 또는 "범위 제외"로 다시 정해지고, 각 항목에 이유가 적혀 있다.
3. **Given** macOS 관련 남은 항목(데이터 이전 시나리오 일부, 레거시 키체인 접근 창, 원저작자 앱과의 공존 설치), **When** 003을 정리하면, **Then** 핵심 플랫폼 항목으로 그대로 남거나 완료 처리되며, 범위 제외로 빠지지 않는다.
4. **Given** 003 스펙, **When** 정리가 끝나면, **Then** 상태가 "Draft"가 아니라 실제 결과(완료 범위, 범위 제외, 남은 macOS 항목)를 반영한다.

### Edge Cases

- 원저작자가 Windows 안내 문장에 이의를 제기하면, 003에서 정한 대응대로 문장을 "Windows를 지원하지 않습니다" 수준으로 줄인다. 이 기능은 그 축소 경로를 깨뜨리지 않아야 한다.
- 메인테이너가 Linux만 포함하거나 Android만 포함한 릴리스를 만들면, 포함된 테스트 빌드 산출물마다 테스트용 표시가 필요하다.
- 테스트용 빌드에만 있는 취약점이 알려졌는데 다음 릴리스까지 고치지 못하면, 그 플랫폼은 다음 릴리스에서 빠지고 이전 릴리스의 해당 산출물에도 취약점 안내가 덧붙는다.
- Android는 서명 키가 등록되기 전까지 매 릴리스에서 빠지지만, 이는 헌법이 정한 상태이므로 연속 누락 횟수에 넣지 않는다.
- Linux와 Android 테스트용 빌드가 모두 실패하면 macOS 산출물만 게시되고, 릴리스 노트에 두 빌드가 모두 없다는 안내가 들어간다.
- 포크 서명 키가 나중에 등록되면, 그 릴리스부터 Android 산출물이 테스트용 표시와 함께 들어간다. 그 전까지의 릴리스에는 Android가 없다.
- 이미 게시된 첫 독립 릴리스(`v1.0.0-alpha.1`)의 Linux 산출물에는 테스트용 표시가 없다. 이 기능은 다음 릴리스부터 표시를 적용하고, 이미 게시된 릴리스는 릴리스 노트에 테스트용 빌드임을 덧붙이는 것으로 정리한다(산출물 파일은 바꾸지 않는다).
- Windows 형식 경로 거부처럼 Windows 이름이 들어가지만 실제로는 모든 플랫폼의 입력 검증인 코드는 "Windows 전용"이 아니므로 남긴다.
- 기존 사용자 데이터 이전 기능 중 Linux 경로는 테스트 빌드 등급이 되었지만, 이미 배포된 Linux 사용자의 데이터를 잃게 해서는 안 되므로 동작은 유지한다. 확인은 자동 테스트로만 하고 실기기 검증은 하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (지원 범위 단일 원문)**: 지원 범위 단일 원문은 헌법 v6.0.0의 네 등급(중점 macOS, 유지 iOS 소스 빌드, 테스트 빌드 Linux·Android, 제외 Windows)을 같은 의미로 담아야 한다(MUST). Windows 문장은 원저작자 앱 안내 한 가지로 한정한다.
- **FR-002 (공개 문구 일치)**: 단일 원문은 한국어 문장과 영문 문장을 함께 제공해야 하며(MUST), 지원 범위를 담는 모든 공개 문서는 한국어 문서에는 한국어 블록을, 영문 문서에는 영문 블록을 원문에서 생성한 그대로 담아야 한다(MUST). 저장소 첫 화면(`README`의 국문·영문판 모두)의 맨 위 영문 배너와 앱 정보 화면도 원문을 따른다. 블록이 원문과 다르면 자동 검사가 실패해야 하며(MUST), 불일치는 0건이어야 한다.
- **FR-003 (이슈 양식)**: 이슈 양식은 Linux·Android 버그 신고를 받아야 하며(MUST), 신고 전에 테스트용 빌드라서 대응 일정을 보장하지 않는다는 안내를 보여 주고(MUST) 해당 신고에 테스트 빌드 표시를 자동으로 붙여야 하며(MUST), Windows는 선택지에 없어야 하고 원저작자 앱 안내 링크만 두어야 한다(MUST).
- **FR-004 (테스트용 빌드 표시)**: 릴리스의 Linux·Android 산출물은 파일 이름과 릴리스 노트 모두에서 테스트용 빌드임을 밝혀야 한다(MUST). macOS 산출물에는 이 표시를 붙이지 않는다.
- **FR-005 (표시 누락 차단)**: 테스트용 표시가 없는 Linux·Android 산출물이 있으면 게시 전 검사가 실패하고 게시되지 않아야 한다(MUST).
- **FR-005a (테스트 빌드 실패 격리)**: Linux·Android 테스트용 빌드가 실패해도 macOS와 성공한 나머지 산출물의 게시를 막아서는 안 되며(MUST NOT), 빠진 테스트용 빌드는 릴리스 노트에 자동으로 밝혀야 한다(MUST). macOS 빌드 실패는 지금처럼 릴리스 전체를 멈춘다(MUST).
- **FR-005b (테스트 빌드 보안 하한)**: 공통 코드의 보안 수정은 macOS와 같은 릴리스에서 테스트용 빌드에도 반영되어야 한다(MUST). 테스트용 빌드에만 있는 알려진 취약점을 그 릴리스에서 고칠 수 없으면, 고칠 때까지 해당 플랫폼을 릴리스에서 빼야 하며(MUST), 보안 정책(국문·영문)과 릴리스 노트에 그 사실을 밝혀야 한다(MUST). 보안 정책은 테스트용 빌드에 대한 이 보장 범위를 명시해야 한다(MUST).
- **FR-005c (연속 누락 제한)**: 같은 테스트 빌드 플랫폼이 3회 연속 릴리스에서 빠지면(빌드 실패나 보안상 제외로 빠진 경우를 센다. Android가 서명 키 미등록으로 빠진 경우는 세지 않는다), 네 번째 릴리스는 게시 전에 멈춰야 하며(MUST) 메인테이너가 그 플랫폼을 고치거나 지원 범위에서 빼는 별도 변경을 결정해야 한다(MUST). 리허설은 이 횟수에 넣지 않는다.
- **FR-006 (Android 서명 유지)**: Android 산출물은 테스트용이라도 포크 소유 고정 서명 키로 서명할 수 있는 릴리스에서만 게시해야 하며(MUST), debug 서명이나 임시 키로 서명한 APK를 게시해서는 안 된다(MUST NOT).
- **FR-007 (이미 게시된 릴리스)**: 첫 독립 릴리스의 릴리스 노트에 Linux 산출물이 테스트용 빌드라는 안내를 덧붙여야 한다(MUST). 산출물 파일과 체크섬은 바꾸지 않는다.
- **FR-008 (Windows 전용 요소 제거)**: 남은 Windows 전용 코드, 설정, 빌드 스크립트, 의존성 감사 대상, 사용 안내 문서를 제거해야 한다(MUST). "Windows 전용"은 동작으로 판단한다: Windows용으로 빌드하거나 실행할 때만 효과가 있는 항목이다. 이름이나 글자에 "windows"가 들어가도 다른 플랫폼에 효과가 있으면(앱 창 목록, 입력 검증, 대소문자 처리 등) Windows 전용이 아니다. 제거 후에도 핵심 빌드와 모든 품질 검사가 통과해야 한다(MUST).
- **FR-009 (보존 대상)**: 다음은 제거하지 않고 보존해야 한다(MUST): 원저작자 앱 안내 문장, 기존 Windows 프리릴리스와 그 산출물·지원 종료 고지, 변경 이력의 지원 종료 기록, 과거 명세와 검증 기록, 지원 종료 고지가 링크한 Windows 전환 안내(갱신하지 않는 보존 기록으로 표시).
- **FR-010 (입력 검증 유지)**: Windows 형식 경로를 신뢰할 수 없는 입력으로 거부하는 보안 검사는 Windows 전용 요소가 아니므로 유지해야 한다(MUST).
- **FR-011 (재유입 방지)**: FR-008 기준의 Windows 전용 요소가 허용 목록 밖에 다시 들어오면 자동 검사가 실패해야 한다(MUST). 검사는 Windows 대상 빌드 설정·Windows 전용 파일 형식·Windows 전용 빌드 분기처럼 동작 기준으로 판별할 수 있는 항목을 대상으로 하며, 단순한 단어 등장만으로 실패해서는 안 된다(MUST NOT).
- **FR-012 (003 정리)**: 003 작업 목록의 열린 항목은 모두 완료, 범위 제외, 다음 기능으로 이관 중 하나로 분류되어야 하며(MUST), 범위 제외와 이관에는 사유와 근거가 있어야 한다(MUST). Windows 전환 검증(T048·T049)은 범위 제외로 표시한다.
- **FR-013 (테스트 빌드 검증 기준)**: Linux·Android 실기기 검증 항목은 "빌드가 만들어지고 설치·실행되는지"만 확인하는 수준으로 낮추거나 범위 제외로 바꿔야 한다(MUST). macOS 항목은 낮추지 않는다(MUST NOT).
- **FR-014 (003 상태 갱신)**: 003 스펙의 상태는 실제 결과(완료 범위, 범위 제외 항목, 남은 macOS 항목)를 반영해야 한다(MUST).
- **FR-015 (기존 데이터 보호)**: Linux 사용자 데이터 이전 기능의 동작은 유지해야 하며(MUST), 테스트 빌드 등급으로 바뀌었다는 이유로 기존 사용자의 데이터를 잃게 해서는 안 된다(MUST NOT). 이 보호는 Linux 경로 규칙(원본 위치, 제외 폴더)을 포함한 자동 이전 테스트(원본 보존, 중단 후 되돌리기, 재실행 시 중복 없음)가 모든 PR에서 통과하는 것으로 확인한다(MUST). Linux 실기기 확인은 요구하지 않는다.

### Key Entities

- **지원 범위 단일 원문**: 플랫폼 등급과 공개 문구의 기준. 한국어 문장과 영문 문장을 함께 가지며, 공개 문서(국문 블록·영문 블록)·배너·앱 정보 화면·이슈 양식이 이를 따른다.
- **테스트 빌드 산출물**: Linux·Android 릴리스 파일. 테스트용 표시(파일 이름, 릴리스 노트)를 가진다.
- **Windows 허용 목록**: Windows가 언급되어도 되는 곳의 목록(원저작자 안내 문장, 지원 종료 이력, 과거 기록, 다른 플랫폼에도 효과가 있는 입력 검증·대소문자 처리).
- **003 작업 항목 분류**: 완료, 범위 제외(사유·근거), 이관(이관처) 중 하나의 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 공개 문서(국문·영문), 영문 배너, 앱 정보 화면, 이슈 양식에서 지원 범위가 단일 원문과 어긋나는 곳이 0건이며, 영문 문서의 지원 범위 블록도 100% 자동 검사 대상이다.
- **SC-001a**: Linux 또는 Android를 고른 버그 신고의 100%가 테스트 빌드 표시를 갖고, 신고 화면에서 대응 일정 미보장 안내가 신고 버튼보다 먼저 보인다.
- **SC-002**: 이 기능 이후 첫 릴리스(또는 리허설)에서 Linux·Android 산출물의 100%가 파일 이름과 릴리스 노트 모두에 테스트용 표시를 갖고, macOS 산출물은 0개가 표시를 갖는다.
- **SC-003**: 테스트용 표시를 일부러 뺀 산출물로 게시 전 검사를 실행하면 100% 실패한다.
- **SC-003a**: Linux 또는 Android 테스트용 빌드를 일부러 실패시킨 리허설에서 macOS 산출물이 100% 게시되고, 릴리스 노트에 빠진 빌드 안내가 1건 이상 들어간다. macOS 빌드를 실패시킨 리허설에서는 게시되는 산출물이 0개다.
- **SC-003b**: 알려진 미수정 취약점이 있는 테스트용 빌드가 새 릴리스에 포함되는 경우가 0건이고, 보안 정책에 테스트용 빌드의 보안 보장 범위가 국문·영문 모두 적혀 있다.
- **SC-003c**: 같은 테스트 빌드 플랫폼이 3회 연속 빠진 상태에서 네 번째 릴리스를 시도하면 100% 게시 전에 멈춘다.
- **SC-004a**: Linux 경로 규칙을 포함한 데이터 이전 자동 테스트가 모든 PR에서 통과하며, 원본 손실·재실행 중복이 0건이다.
- **SC-004**: 게시된 Android 산출물 중 포크 서명 키가 아닌 키로 서명된 것이 0개다.
- **SC-005**: 허용 목록 밖에 남은 Windows 전용 요소가 0건이고, 제거 후 macOS 핵심 빌드와 모든 품질 검사가 통과한다.
- **SC-006**: 기존 Windows 프리릴리스, 그 산출물, 지원 종료 고지, 고지에서 링크한 안내 문서가 100% 그대로 열린다.
- **SC-007**: 003 작업 목록의 열린 항목 중 분류(완료, 범위 제외, 이관)가 없는 항목이 0개이고, 003 스펙 상태가 실제 결과와 일치한다.
- **SC-008**: Windows 형식 경로를 담은 입력 거부 검사가 이 기능 전과 같은 결과를 낸다(회귀 0건).

## Assumptions

- "테스트용 빌드" 표시는 파일 이름에 붙는 짧은 표식과 릴리스 노트의 한·영 안내 문장으로 충분하다고 본다. 표식의 구체적인 형태는 계획 단계에서 정한다.
- 이미 게시된 첫 독립 릴리스의 Linux 산출물은 파일 이름을 바꾸지 않는다. 체크섬과 링크를 깨뜨리지 않기 위해서다. 대신 릴리스 노트에 안내를 덧붙인다.
- 지원 종료 고지가 링크한 Windows 전환 안내는 사용자가 지시한 "지원 종료 이력 보존"에 속한다고 보고 삭제하지 않는다. 헌법의 "사용 안내 문서 제외"와 충돌하지 않도록 갱신하지 않는 보존 기록으로 표시한다.
- Windows 형식 경로를 거부하는 입력 검증은 macOS·Linux에서도 들어오는 입력을 막는 제로 트러스트 검사이므로 Windows 전용 요소로 보지 않는다.
- 저장소 이름 `EasyViewer`와 내부 저장 키는 003의 결정대로 바꾸지 않는다.
- Android 서명 키 생성(003 T062)은 메인테이너 작업으로 남으며, 이 기능의 완료 조건이 아니다.
- iOS 등급(유지, 소스 빌드만)과 macOS 등급은 이 기능에서 바꾸지 않는다.
